How access works

How Knowva enforces permissions cryptographically at the server layer without trusting client-side state.

1 Discrete Capabilities

The app asks what you can do, not what role you are

Actions and UI components query discrete atomic permission capabilities instead of coarse static labels. Whether a user is acting as an Exam In-charge or Bursar, specific calls like marks.lock and fees.concession.approve are checked independently.

policy_engine.ts Client State Agnostic

// Coarse check rejected: if (user.role === 'Principal')

const canLockGradebook = await authGuard.evaluateCapability({

action: "cbse.gradebook.freeze",

tenantId: session.institutionRef,

campusScope: session.campusId,

actorClearance: session.ephemeralKey

});

2 Tenancy Ingress Enforcer

Hidden is not the same as allowed, the server always checks

Hiding a UI element in the browser is just a layout affordance. Every single incoming API endpoint executes an immutable, server-side authorization check against the school’s active tenancy policy before processing data payloads.

3 Institutional Hand-off

“Done by …” instead of dead ends

When an educator or staff member encounters a restricted workflow, Knowva never presents a generic 403 error. Instead, it provides an institutional routing card indicating exactly which desk holds authority (e.g., “Done by the Registrar”), eliminating administrative confusion.

4 Field-Level Redaction

Field-level restriction for pay and statutory IDs

Sensitive identifiers—including teacher basic pay schedules, student Aadhaar numbers, PF allocations, and confidential medical history—are masked at the database serializer level prior to payload transmission.

5 Immutability & Dual Sign-off

Governed role changes with a reason, history and no self-promotion

Super-administrators cannot grant permissions to themselves. Every permission assignment requires a dual sign-off workflow, mandatory written reason tagging, and immutable append-only commit logs.
